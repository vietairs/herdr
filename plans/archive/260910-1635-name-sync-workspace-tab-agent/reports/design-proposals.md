## Policy A — Rename Is A Permanent Pin, Everything Else Auto-Derives

Policy A makes today's accidental behavior the explicit, uniform contract: any name a user types is a permanent pin that nothing overwrites, and every name the user has NOT typed is re-derived from the owning cwd on the existing periodic refresh path. It closes D1 by giving tabs a cwd/git-root auto-name (reusing derive_label_from_cwd, src/workspace/git/discovery.rs:23-27) instead of the bare ordinal at src/workspace.rs:478-484; it closes D2 not by unfreezing renamed workspaces but by declaring the freeze intentional and making it reachable/reversible; it closes D3 in one direction only — a tab rename propagates DOWN to TerminalState::agent_name (src/terminal/state.rs:133) for panes whose agent name is itself derived, never onto a user-set one. The structural argument for A is that its central bit already exists end-to-end: ClientShellWorkspace.custom_label and ClientShellTab.custom_label (src/protocol/wire.rs:1063, 1096) are already populated server-side (src/server/client_shell.rs:64, 108) and already drive client styling, so A adds no new concept to the runtime/client protocol. Its two honest costs are that "rename" is not currently synonymous with "user intent" (worktree and layout flows call set_custom_name too), and that agent_name carries no user-vs-derived provenance at all today.

**Rules**
- A workspace with no user pin re-derives its label every git-refresh cycle from tab 1's root-pane cwd; the resolved label already flows through actions.rs:1550-1555 into Workspace::cached_auto_label and out via display_name_from (src/workspace.rs:1086-1093).
- A user rename sets a permanent pin. It is never overwritten by derivation, by a cd, by a git-root change, or by a propagation from any other namespace. Only an explicit clear/reset verb returns that name to auto — and that verb does not exist today for workspaces or tabs (src/app/api/workspaces.rs:863 only ever calls set_custom_name), so Policy A must add it.
- A pin must be distinguished from a seeded name. set_custom_name is today also called by worktree creation (src/app/api/worktrees.rs:149), workspace-create-with-label (src/app/api/workspaces.rs:717), tab-create-with-label (src/app/api/tabs.rs:164) and layout apply (src/app/api/layouts.rs:144). Under Policy A those seeds are marked seeded, not pinned, and keep auto-syncing; otherwise every worktree space is born permanently frozen.
- A tab with no user pin derives its label from that tab's OWN root-pane cwd via Tab::cwd_for_pane (src/workspace/tab.rs:532-547) plus derive_label_from_cwd; the (tab_idx + 1) ordinal at src/workspace.rs:481-483 survives only as the last-resort fallback when no cwd resolves.
- Derived names are never written into custom_name and never persisted. A session save fires on every rename and dirty mark (src/app/api/tabs.rs:171, src/app/api/panes.rs:1788), so writing a derived label into TabSnapshot.custom_name (src/persist/snapshot.rs:85-87) would silently convert every tab into a permanent pin at the first save — the single worst failure mode of this policy.
- A tab rename propagates down to TerminalState::agent_name only for panes in that tab whose agent name is Derived (set by detection, hook authority, or a managed launch). A User-sourced agent name is never overwritten, and a pane with no agent is never given one — agent.rename itself already refuses that at src/app/agents.rs:127-129 with AgentRenameError::NotAgent.
- All derivation runs server-side on the existing periodic git-refresh path (src/app/git_refresh.rs:114-132 collecting, src/app/actions.rs:1526-1573 applying). Nothing derives during compute_view or render: Tab::cwd_for_pane can reach PaneRuntime::cwd, which falls back to platform::process_cwd(pid) (src/pane.rs:3806-3823), a live process probe banned in pane-scaled loops.
- Propagation is one-directional and lossless-by-construction: tab -> agent only. Workspace -> tab, tab -> pane label, and agent -> tab are explicitly out of scope, so no propagation can ever destroy a name the user typed and no undo affordance is required.

**User-visible change**

A tab that has never been renamed stops showing a bare number and starts showing its own git-root or directory name, refreshed on the same ~1.5s cycle that already updates space names — so a space with three tabs in three worktrees reads "herdr / herdr-name-sync / herdr-fed" instead of "1 / 2 / 3". A space with no user-typed name keeps following the cwd exactly as it does today, including after a cd, but only when that cd happens in tab 1's root pane (resolved_identity_cwd_from reads self.tabs.first(), src/workspace.rs:1052-1056) and only to a basename until the next refresh climbs to the git root (automatic_display_name_for_cwd falls back to fallback_label_from_cwd on a cache miss, src/workspace.rs:1099-1105). Anything the user renames by hand stops moving for good and is marked as pinned on the wire the same way it already is (custom_label, src/protocol/wire.rs:1063 and :1096) — and to undo a pin the user needs a new clear/reset verb that does not exist yet. Renaming a tab also relabels the agents inside it whose names came from detection rather than from the user, so the agent sidebar rows follow the tab; an agent the user named by hand is left alone. Names reaching notifications (src/server/notifications.rs:48), the OS window title (src/app/window_title.rs:63, :68) and plugin context (src/app/api/plugins/context.rs:248) all change with them.

## Policy B: Project-Anchored Rename Pin

A rename stores the name together with the project it was typed in (git checkout key from GitSpaceMetadata, or the cwd when not in a repo). The name holds while the resolved identity cwd stays in that project and is dropped the moment it crosses into a different one, at which point auto-derivation resumes. Tabs gain a cwd-derived auto label to replace the bare ordinal at src/workspace.rs:478-484, and a tab rename overwrites agent names in that tab only where the agent name is still auto-derived. All evaluation runs on the existing 1.5s git-refresh path in server state, never in render.

**Rules**
- Rename stores a project anchor. Workspace::custom_name (src/workspace.rs:1038 set_custom_name) and Tab::custom_name (src/workspace/tab.rs:204) each gain a sibling anchor recording the GitSpaceMetadata.checkout_key at rename time (src/workspace/git/discovery.rs:6-13), or the resolved cwd when git_space_metadata returns None.
- Staleness is evaluated only on the existing background refresh. AppState::apply_workspace_git_statuses (src/app/actions.rs:1525-1572) already receives a freshly discovered result.space and result.auto_label from the thread spawned in src/app/git_refresh.rs:65-72. Comparing result.space against the stored anchor there adds zero work to render and no filesystem I/O on any pane-scaled loop.
- Anchor mismatch clears the pin. Replace the freeze at src/app/actions.rs:1555 (changed |= ws.custom_name.is_none()) with: if the incoming project differs from the anchor, drop custom_name and set changed = true; otherwise keep the pin and leave changed as today. The auto label then flows through the untouched Workspace::display_name_from (src/workspace.rs:1085-1097).
- Tabs auto-derive from their own root pane cwd. src/workspace.rs:478-484 tab_display_name returns (tab_idx + 1).to_string() today; it must instead clone a Tab::cached_auto_label filled by the refresh cycle, mirroring Workspace::cached_auto_label (src/workspace.rs:218). tab_display_name stays a pure infallible clone because its callers (src/app/window_title.rs:68, src/app/creation.rs:236, src/app/api/plugins/context.rs:248) sit on presentation paths.
- The ordinal survives as the last-resort fallback. When no cwd resolves for a tab root pane via Tab::cwd_for_pane (src/workspace/tab.rs:532-547), tab_display_name still yields (tab_idx + 1).to_string() so a tab is never blank and existing tests keep a defined answer.
- A tab rename propagates only to derived agent names. TerminalState::agent_name (src/terminal/state.rs:133) is currently indistinguishable between hook-set, session-restored and user-set values because set_agent_name (src/terminal/state.rs:1883-1908) populates agent_name_owner in all three cases. Policy B therefore adds an explicit provenance discriminator and overwrites only the Derived variant, never a hook authority value produced by reconcile_agent_name_owner (src/terminal/state.rs:1919-1926).
- Agent kind labels are never touched. effective_agent_label (src/terminal/state.rs:1812-1823) resolves the agent kind (claude, codex) from hook authority or detection; it stays detection-owned, so the change cannot regress the manifest contract described in CLAUDE.md.
- Everything lands in server state and the JSON API event path. Anchors live on Workspace and Tab, unpin events emit next to EventKind::WorkspaceRenamed (src/app/api/workspaces.rs:865-872) and EventKind::TabRenamed (src/app/api/tabs.rs:334-341) under neutral names such as WorkspaceLabelChanged with a label_source field, so CLI, TUI and federation peers observe one truth. No behavior is added behind the private TUI client socket.
- Remote-mounted workspaces never auto-unpin. src/server/federation_accept.rs:847 already reasons about host set_custom_name versus mounted rows; an unpin driven by a peer pane cwd would rename a workspace under the peer's feet, so the anchor check is skipped for mounted workspaces.

**User-visible change**

Workspaces and tabs both show the repo or folder name they are actually sitting in, and that name keeps following the cwd even after the user has renamed once. A rename still wins while the user stays in the same project, but the moment the workspace moves to a different project the typed name is dropped and the derived name takes over. Tabs stop reading as bare ordinals (1, 2, 3) and read as project names instead, and renaming a tab renames the auto-named agents inside it.

## Policy C — one shared derivation chain with explicit precedence at every layer

Replace the three independent naming fields with one server-side resolver plus one override store. `resolve_name(scope, sources) -> {text, source}` applies a single documented ladder — user override (inheritable down-scope) > agent identity > cwd/git-root > ordinal — uniformly to workspace, tab and pane/agent. Today the same ladder is hand-written three times with different rungs: `Workspace::display_name`, `display_name_from_terminals` and `display_name_from` (src/workspace.rs:1059, 1067, 1085) each open with an identical `if let Some(name) = &self.custom_name { return name.clone(); }` and then diverge on how they find a cwd; `tab_display_name` (src/workspace.rs:478-484) has only rungs 1 and 4 and skips cwd entirely; and the agent label resolves through a fourth, unrelated chain in `TerminalState::effective_agent_label` (src/terminal/state.rs:1812-1824). Under C, renaming a tab writes one override that descendant panes read at resolve time, so the agent's displayed label follows without any write to `TerminalState::agent_name`. Derivation input stays on the existing ~1.5s git-status pass (src/app/actions.rs:1526-1571), never on the render path. The honest cost is blast radius: ~30 call sites, four struct changes, three API schema changes, and a direct conflict with an existing test that asserts agent name and pane label are independent (src/app/api/agents.rs:699-725).

**Rules**
- Precedence ladder, identical at every scope, highest first: (1) user override at this scope, or inherited from the nearest enclosing scope that was renamed; (2) agent identity; (3) cwd / git-root derivation; (4) stable ordinal. Every read of a name goes through the resolver — `Workspace::custom_name`, `Tab::custom_name` and `TerminalState::manual_label` remain as storage but stop being read directly anywhere, which is exactly what today's three near-duplicate chains at src/workspace.rs:1059/1067/1085 fail to do.
- Only overrides are authoritative state; derived names are never stored as truth and never persisted. Rung 3 reads a cached field refreshed on the existing periodic git pass, matching how Workspace already works (cached_identity_cwd / cached_auto_label, src/workspace.rs:212-218, refreshed at src/app/actions.rs:1550-1552). Tabs gain the same pair, which is the whole of D1 — they currently have no cwd field at all (src/workspace/tab.rs:38-51), which is why they can only emit an ordinal.
- The resolver is a pure function and derivation input never enters a render or pane-scaled loop. Resolving reads cached scalars only; the expensive half (git_repo_root, and PaneRuntime::cwd falling through to platform::process_cwd at src/pane.rs:3806-3824 when OSC 7 has not reported) runs only in the existing WorkspaceGitStatus pass at src/app/actions.rs:1526-1571, which tabs join rather than duplicate.
- A rename pins a name but never stops derivation underneath it. src/app/actions.rs:1554's `changed |= ws.custom_name.is_none();` gates only the redraw signal — :1551-1552 already refreshes cached_auto_label unconditionally, so a renamed workspace is sitting on a live derived label nothing reads. C makes that label reachable via the resolver's source field, so clearing an override snaps to the correct current name with zero refresh delay.
- Renaming propagates by shared resolution, never by copying strings between fields. A tab override is read by descendant panes at resolve time; it is never written into TerminalState. Writing it would make one rename irreversibly destroy pane-scope overrides, and any such write reachable from a draw path would violate the pure-render rule.
- The agent's display label and the agent's addressable handle are separated explicitly. The label resolves through the ladder and follows a tab rename; TerminalState::agent_name stays a distinct identifier so `herdr agent send <name>` keeps working and the uniqueness and charset rules survive (valid_agent_name ^[a-z][a-z0-9_-]{0,31}$ at src/app/agents.rs:15-21, agent_name_conflicts at :404-416 — neither of which tab or workspace names are subject to).
- An inherited tab override does not clobber a hand-set agent name. Inheritance applies only where agent_name_owner indicates the name was auto-assigned or detection-owned (src/terminal/state.rs:134, 1886-1908), never where the user set it via agent.rename. This is a deliberate exception to uniformity and must be documented as such rather than hidden.
- The ordinal rung uses stable identity, not position: tab.number via public_tab_number (src/workspace.rs:1010-1012), not `tab_idx + 1` as tab_display_name does today (:478-484), so a tab's fallback name stops changing when tabs are reordered.
- Resolution stays server-side and ships resolved on the JSON API path, per the runtime/client boundary rule. It lives in a new src/workspace/naming.rs beside aggregate.rs and feeds the sites that already assemble labels (src/app/creation.rs:236 and :411, src/app/api.rs:686 and :984, src/server/notifications.rs:48, src/app/window_title.rs:63-76). TabInfo/WorkspaceInfo/PaneInfo carry a NameSource discriminant so clients style a derived name differently without ever re-deriving it; nothing lands in the TUI client.

**User-visible change**

A workspace the user never renamed keeps following its cwd exactly as today — that machinery already works (src/app/actions.rs:1550-1552 refreshes the cached label on the ~1.5s git pass; src/workspace.rs:1099-1105 falls back to a live basename on cache miss). A renamed workspace still stays pinned to the chosen name, but for the first time the derived name is observable alongside it and clearing the override snaps straight back to the correct current project with no refresh delay, because the derived label was kept live underneath the whole time. Tabs change most: instead of the bare ordinal from `(tab_idx + 1).to_string()` (src/workspace.rs:478-484), a tab shows the git-root or basename of its root pane's cwd — and where that cwd is a descendant of the workspace's own, the path suffix relative to it, so a single-repo workspace does not render four tabs all reading "herdr". The ordinal survives only when no cwd resolves, and becomes the stable tab.number (src/workspace.rs:1010-1012) rather than a positional index, so a tab's fallback name stops changing when tabs are dragged. Renaming a tab immediately changes the label shown for every agent pane inside it that has no pane-scope name of its own, at the next resolve, with no refresh cycle. What it does not change is the agent's addressable handle: TerminalState::agent_name is untouched, so `herdr agent send reviewer` keeps working and the uniqueness and charset rules at src/app/agents.rs:15-21 and :404-416 still hold. That split — the label follows the tab, the handle does not — is the deliberate compromise, and it is the part of the original request C does not deliver in full.

**Risks**
- Blast radius is the largest of the candidates and is refactor-risk by CLAUDE.md's own definition (two-plus core surfaces, persisted state, API IDs, identity projection). tab_display_name has 8 callers (src/app/actions.rs:228, src/app/creation.rs:236, src/app/window_title.rs:68, src/app/api/plugins/context.rs:248/309/335, plus tests); the display_name_from* family has ~10 (src/app/api.rs:686 and :984, src/app/creation.rs:411, src/server/notifications.rs:48, src/server/headless.rs:3387, src/server/headless/notifications.rs:108 and :183, src/app/actions.rs:2118, src/app/window_title.rs:63); manual_label is read at 12+ sites spanning persist, client_shell, plugins and layouts. Characterization tests and AppState::assert_invariants_for_test must land before any code moves.
- It contradicts an invariant the codebase asserts on purpose. src/app/api/agents.rs:699-725 (`agent_rename_does_not_replace_the_pane_label`) exists to keep agent name and pane label independent. C keeps the stores independent but couples their resolution, so that test still passes while its stated intent now reads backwards to anyone who opens it. It needs rewriting with an explicit comment or it becomes an actively misleading signal.
- The 'uniform precedence' claim cannot be fully kept, and pretending otherwise is the main way this policy fails review. Agent identity already has its own two-tier authority chain (hook authority over detected agent, src/terminal/state.rs:1812-1824); the agent handle carries validation and server-wide uniqueness the other scopes lack (src/app/agents.rs:15-21 and :404-416); and the do-not-clobber-a-hand-set-agent-name carve-out is a further conditional keyed on agent_name_owner. The result is one function with several scope-specific branches — better than three chains, but not the clean thing the name promises.
- Tab-override inheritance must be computed at read time, never written into pane fields, or one rename irreversibly destroys pane-scope overrides. Read-time inheritance is correct but requires both tab and pane context at every call site, and several current sites hold only a TerminalState (src/server/client_shell.rs:469-472, src/app/api/plugins/panes.rs:39) — those need plumbing or a degraded resolve.
- Cost is paid before value is visible. D1 alone (a tab cwd cache plus rung 3) and D2 alone (a clear path plus an observable derived name) are each independently shippable and deliver most of the user-visible benefit; C bundles them behind a refactor that must land atomically to be coherent, so a mid-way abort leaves the tree worse than either narrow fix would.
- Persisted numeric tab overrides become ambiguous after upgrade. A TabSnapshot.custom_name of "3" is indistinguishable from an ordinal a user deliberately typed, so post-upgrade that tab pins "3" while its siblings become "herdr"/"docs". Nothing corrupts and the snapshot carries no evidence to disambiguate. Recommendation is to honor it as the override it is; the alternative — dropping tab overrides equal to their own ordinal at restore — deletes user data on a heuristic and should not ship without asking.
- Federation is unquantified in this pass. Fork history records pane and tab identity crossing the federation wire, so a resolved-label-plus-source contract has to be decided for mounted remote panes (does a local tab rename apply to a remote tab's panes, and does the source discriminant survive the wire?). I did not open the federation code, so this is flagged as unsized rather than estimated.
