Ship-Gate Explainer — Federation Pane-Close Sync (protocol v3→4)

TL;DR

Closing a pane now works bidirectionally across a herdr federation link. A close on a mirrored remote pane sends a ClosePaneRequest over the Control channel to the serving host (Gap A), and a pane removed on the serving host now tears down its mirror on the client even for mount-time panes (Gap B — a bug in the existing resync index, fixed by registering panes at build time). Protocol version bumped 3→4 because v3 shipped in release v0.7.5-hvn.1.

Context

Plan: plans/260724-1536-federation-pane-close-sync/plan.md. Prior workaround was closing the pane over ssh and remounting. Memory note herdr-federation-no-pane-close-wire-message documented the gap; this diff closes it.

Intuition

The close path mirrors the existing SplitPane pattern end-to-end: client resolves the pane target, mints a pending-close entry, sends ClosePaneRequest; the serving host resolves and closes locally (refusing, read-only, any close that would need a local confirmation modal — federation origin can never answer one); response comes back as ClosePaneReady/Failed, with a structured pane_not_found: reason folded into idempotent success. Gap B fix: build_remote_pane now populates remote_resync_pane_index so the existing removal handler covers mount-time panes.

Blast Radius

  • Wire protocol v4 — both ends (local + VM servers) must be rebuilt together after merge; a v3 server will refuse v4 mounts.
  • Touched: protocol types/codec, federation actor + accept loop on the server, client dispatch, app close path (app/api/panes.rs), pane creation/teardown (creation.rs), loopback test fixture.
  • Known documented limitation: chained mounts (A→B→C) close propagation — pre-existing, documented, not fixed here.
  • No suspicious embedded content, no secrets in the diff.
