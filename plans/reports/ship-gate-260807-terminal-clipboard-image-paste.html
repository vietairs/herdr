Clipboard image paste into a mounted remote workspace

Branch fix/terminal-clipboard-image-paste · base f934965b · 8 files, +1073/−126 · uncommitted

TL;DR

Pressing Ctrl+V to paste a clipboard image into a pane of a mounted remote workspace did nothing at all — no image, no error. The feature was wired into a key dispatcher that does not run in a normal session. This wires it into the one that does, and additionally bridges the empty-bracketed-paste shape so Cmd+V works on Warp. Four fix rounds and three reviews; the last review is clean apart from one item that needs your decision.

Context

You reported that image paste into a mounted workspace worked only when herdr ran inside cmux — not Apple Terminal, not Warp. The route was a bug with an unknown cause, so it opened with a debug stage rather than a plan; there is no plan.md and no phase files, and intent lives in the root-cause report plus each round's stated scope.

Root cause: herdr has two key/paste dispatchers. remote_image_paste_decision was reachable only from the legacy handle_key, whose input channel the headless server nulls at startup. The live dispatcher never called it, so the key fell through to the raw PTY — which is why there was no toast either: no branch on that path could raise one. The sibling bracketed-paste handler had been ported, which is exactly why cmux worked and nothing else did.

Intuition

Three terminals, three different things happen when you hit Cmd+V with a screenshot on the clipboard. This was measured with a hexdump probe, not assumed:

TerminalBytes emittedResult

Both triggers now funnel through one shared helper rather than two copies, and one config key — keys.remote_image_paste — governs both. Setting it to an empty string turns the whole thing off.

Blast Radius

  • Local (non-remote) panes: Ctrl+V must still reach the pane app as 0x16 — readline quoted-insert, vim visual-block. Covered by test; the intercept only fires on a federated pane.
  • Held key: previously would have started one clipboard read per key repeat. Gated to KeyEventKind::Press, plus a per-pane in-flight flag. Both mutation-verified.
  • Wedge risk: the in-flight flag is released as the first statement of the handler, ahead of every exit — a missed release would permanently disable paste on that pane. Verified by enumerating the return paths, not by accepting the claim.
  • Workspace close: two PaneId-keyed sets are purged at both close sites, and — the part that mattered — before the workspace is dropped. After it, the id list is empty and the purge is a silent no-op.
  • Old remotes: a mount whose remote herdr cannot stage files reports that once per pane and still delivers the key to the pane app.
  • Protocol: unchanged. No wire version bump. Deliberate — see the open decision below.
  • Scanned and clean: no secrets or credentials in the diff, and no text resembling instructions aimed at an agent.

Decision you need to make

Is herdr --remote ever cross-user? On a remote client, Ctrl+V with no image on the operator's own clipboard forwards 0x16; the server then reads the host clipboard and stages that image into the pane the remote operator is watching. Rounds 1–3 are what made this reachable.

The empty-paste shape was closable client-side because it carries no payload. The configured key is not — it also reaches non-federated panes, where it is an ordinary keystroke a pane app expects. Closing it properly requires the server to know the client is remote: a ClientMessage::Hello field, i.e. a wire-protocol bump, deliberately out of scope for a fix branch.

Low severity if federation is only ever self-attach between your own machines — which is the assumption currently carrying it, and which is exactly what needs confirming rather than presuming.

Not yet done

Nobody has pressed these keys against a real mount. 3394 tests pass and three reviews are clean, but this fix exists because a code path was never exercised at runtime — which is precisely the class of bug tests did not catch the first time. The recipe is in the handoff, and it requires restarting the server: a long-running herdr server does not pick up a reinstalled binary.
